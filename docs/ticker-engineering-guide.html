Ticker

A single-machine stock dashboard: live prices streamed to the browser, a portfolio derived from an append-only ledger, and an AI analyst that can propose changes but never make them. This guide covers the architecture end to end, how each layer works, and how the system was built.

Project at a glance

Five layers, one process, three rented services

Everything below the browser runs as a single Python process on a single machine. That is a deliberate constraint, not a limitation of scale: the market feed allows one connection per key, and the database is a file on a disk that cannot be mounted twice.

Data layer Rented feeds + SQLite Finnhub, Twelve Data, Anthropic. Local state in one SQLite file on a Fly volume.
Processing layer Providers + services Provider interface, TTL cache, price hub, FIFO lot engine, chat loop.
Application layer FastAPI 14 REST routes, one WebSocket, one SSE stream, all behind a session gate.
Visualisation layer React + lightweight-charts Zustand for high-frequency prices, TanStack Query for REST.
Output layer One page, one origin The API serves the built SPA, so there is a single deploy and no CORS.
Invariant Transactions are truth Positions, cost basis and P/L are all recomputed; nothing is stored twice.

The three paths a change can take through the system

Everything the dashboard does is one of three flows. They share the same services but differ in what starts them and what they are allowed to touch: only the portfolio path and the final step of the chat path write to the ledger.

How the system was built: a spec-driven loop with four feedback channels

The project was written by an AI agent — Claude Code, running Claude Opus 5 — against a specification authored before any code existed. There is no autonomous task-runner here: each phase was a deliberate, human-initiated cycle. What makes the loop a loop is the four distinct ways a defect got discovered, three of which only fire after the code is already deployed.

Dependencies

The four outside services, and what each is for

Finnhub — the price feed

Free tier
Does what
Live prices and symbol search. Holds one permanently open connection to the market and pushes every trade through it.
Why this one
The only free service offering genuinely real-time US prices over a push connection. Most free tiers are delayed, or make you poll.
The catch
Its free tier stops at live prices. History is a paid feature — discovered only after deploying, when the request came back refused.
Without it
No live prices. Cost basis and realized P/L are unaffected; they come from your own ledger.

Twelve Data — the history

Free tier
Does what
Past prices — the daily closes behind both charts. Nothing live.
Why it exists
Purely to fill Finnhub's gap. Rather than pay for history, a second provider answers that one question, behind the same interface.
Why this one
800 requests a day free. The obvious alternative allows 25 — six clicks on the chart range buttons would exhaust a day.
Without it
Both charts return a 502 that names the fix. Everything else is unaffected.

Anthropic — the analyst

Pay per use
Does what
Powers the chat. It can read holdings, check prices, read transaction history and search the web, then answer in plain language.
The important part
It can propose portfolio changes but cannot make them. Nothing is written until you click Confirm.
Why that matters
Not distrust of the model. "Sell everything," typed at 2am, should meet a confirmation dialog like any other destructive action.
Without it
The chat panel returns 503. The dashboard works normally.

Fly.io — where it runs

~$3/month
Does what
Runs the container on one always-on machine with a public address and HTTPS. Hosting, not a component.
Why this one
It keeps a long-lived connection open. Hosts that sleep between visits would kill the market socket every time you looked away.
Also provides
A volume — a disk that survives restarts. The database lives there; without it every deploy would wipe the ledger.
Without it
The app runs on a laptop, reachable only by you, only while it is awake.

Constraints

Five decisions that shaped everything else

  • Exactly one machine — for correctness, not cost
    Two copies would open two connections to a feed that allows one, and each would keep its own database on a volume that cannot be double-mounted. The config pins it explicitly rather than relying on a default.
  • The transaction log is the only source of truth
    Holdings, average cost and P/L are recomputed from the list of buys and sells every time. The log is append-only; a correction is a new row or a delete-and-rebuild. There is deliberately no stored share count, because average cost loses information the moment you sell part of a position.
  • The model proposes; the person disposes
    Enforced structurally: the tool dispatcher receives a narrow read-only reader, never a database connection, so it cannot write. A test runs every tool and asserts the ledger is byte-for-byte unchanged.
  • It reports; it never advises
    The system prompt forbids recommendations, price targets and predictions. Asked whether to sell, it declines and offers data. Every answer carries a disclaimer.
  • Degrade honestly, never guess
    A price that is unavailable renders as an em dash, not a zero. Stale quotes are labelled with their age. A dead provider leaves market value null and names the symbols it could not price, rather than blanking the portfolio.

Migrations run at boot, idempotently — never as a release command, because that machine runs with no volume attached and the work would vanish. A nightly snapshot writes beside the live database using SQLite's online backup, not a file copy: with write-ahead logging, copying the database without its journal yields a torn file that looks fine until you need it.
